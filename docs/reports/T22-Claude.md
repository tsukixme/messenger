### 3. Безопасность — воспроизведено без сети, с программными заглушками

Для каждого пункта: заглушки `fastapi.HTTPException/Request/Response`,
`pydantic.BaseModel`, `httpx.AsyncClient` (в памяти, без реальных запросов) —
код `auth/app.py` подключался как есть, без изменений. Переменные окружения
с «секретами» — заведомо фиктивные строки `***`, `x.ngrok-free.app` и т.п.

**P1. Критично: подделка подтверждения номера, если `WA_APP_SECRET` не задан.**
Файл: `auth/app.py:183-203` (`webhook`), условие `if WA_APP_SECRET:` на
строке 186. Если переменная окружения пуста (а в `.env.example:22` она пуста
по умолчанию), проверка подписи целиком пропускается, и `POST /auth/webhook`
принимает **любое** тело от **любого** отправителя без аутентификации.
Воспроизведено: `start()` для номера `+77011234567` → `webhook()` вызван с
самодельным JSON вида WhatsApp-уведомления, без заголовка
`X-Hub-Signature-256` → `status()` вернул `verified: true` и готовый
`user_id`/`password` для аккаунта Matrix на этот номер.
Результат прогона: `P1 forged webhook, no signature -> TAKEOVER
@u77011234567:x.ngrok-free.app`.
Когда `WA_APP_SECRET` задан — то же самое с неверной подписью отклоняется
(`403`), а с верной подписью проходит штатно; я это тоже проверил (раздел
«P3» ниже). То есть **механизм подписи реализован правильно**, проблема
только в том, что `.env.example` и README не требуют явно, что
`WA_APP_SECRET` обязателен для публикации сервера в интернет — при
забытом/пустом значении защита тихо выключается.
Риск: любой, кто знает (или подберёт) публичный URL `/auth/webhook`, может
выписать себе логин и пароль Matrix на **чужой** номер телефона, не имея к
нему доступа, то есть захватить учётную запись. Это худшее из найденного.

**P2. `DEV_MODE` — предусмотренная лазейка, а не баг, но требует внимания при
деплое.** `auth/app.py:213-218`. При `DEV_MODE=true` (значение по умолчанию в
`.env.example:14`!) эндпоинт `/auth/dev/message` делает ровно то же самое, что
P1, но без необходимости подделывать формат Meta — одним `POST` с `{phone,
text}`. Воспроизведено: вызов `dev_message` с номером и кодом другого
пользователя → `{"verified": true}`.
При `DEV_MODE=false` тот же вызов возвращает `404` (проверено: «P2
/auth/dev/message -> 404»). Это именно то, для чего эндпоинт задуман (ручная
проверка без WhatsApp), но `.env.example` ставит его включённым по умолчанию,
а README не содержит явного «ОБЯЗАТЕЛЬНО выключить перед публикацией» рядом
с инструкцией по запуску — сейчас это упомянуто только в середине текста
README. Нужно усилить: shipping-чеклист должен требовать `DEV_MODE=false` и
непустой `WA_APP_SECRET` как условие перехода на публичный домен.

**P3. Проверка подписи сама по себе корректна.** `hmac.compare_digest` —
правильный выбор (защита от атаки по времени сравнения). Воспроизведено:
неверная подпись → `403`; корректная HMAC-SHA256 подпись тем же секретом →
принято, `verified: true`. Замечаний нет, кроме того, что P1 делает эту
проверку необязательной при пустом секрете.

**P4. Нет общего лимита на `/auth/start`, только лимит на один номер.**
`starts` (словарь `phone -> [timestamps]`, строка 45) ограничивает 5 попыток
в час **на конкретный номер** (`MAX_STARTS_PER_HOUR`, строка 42), но ничего
не ограничивает число **разных** номеров с одного IP или вообще в целом.
Воспроизведено: 20 000 вызовов `/auth/start` с 20 000 разных номеров
выполнились без единой ошибки, `sessions` и `starts` выросли до 20 001
записей каждый, процесс не упал, но и не освобождает память иначе как через
`cleanup()` при следующих вызовах. Это не критично для пилота (трафика
почти нет), но является reasonable DoS/расход SMS-подобных WhatsApp-сообщений
риском при публичном домене: кто угодно может завести очередь кодов на чужие
номера (жертва получит спам в WhatsApp с нашими кодами) или просто раздуть
память процесса. Нет лимита по IP и нет общего глобального лимита запросов.

**P5. Нормализация телефонов не ограничена кодом страны.** `normalize_phone`
(строка 52-61) трактует любые 10 цифр как российский/казахстанский номер,
добавляя `7` спереди. Воспроизведено: `normalize_phone("2025550123")` (это
американский формат, 10 цифр) → `72025550123` — то есть чужой номер другой
страны молча превращается в число, похожее на казахстанский номер. Если
значение дальше совпадёт с кем-то реальным, можно создать путаницу или
коллизию `user_id`. Для пилота в РК это не блокер, но стоит явно
задокументировать как ограничение, а не оставить как неочевидный побочный
эффект.

**P6. При сбое Synapse сессия необратимо теряется.** `GET /auth/status/{sid}`
удаляет сессию из `sessions` *до* вызова `ensure_matrix_user` (строка 167-168:
`del sessions[sid]`, затем `await ensure_matrix_user(...)`). Если в этот
момент Synapse ответит ошибкой (сеть, перегрузка, неверный токен), клиент
получит `502`, но повторный вызов `status` для того же `sid` вернёт уже `410`
("Сессия истекла"), и пользователю придётся начинать вход заново, хотя номер
уже был подтверждён. Воспроизведено: подтверждённая сессия → Synapse отвечает
500 → `502` клиенту → тот же `sid` повторно → `410`. Это не угроза
безопасности, а дефект надёжности (плохой UX и источник обращений в
поддержку), но учитываю его, т.к. задача просила также проверить «обращение к
Synapse admin API».

**Admin API / выдача токена.** `ensure_matrix_user` (строка 97-116) всегда
выдаёт **новый случайный пароль** (`secrets.token_urlsafe(24)`, 24 байта
энтропии — этого достаточно) через `PUT
/_synapse/admin/v2/users/{user_id}` с `Authorization: Bearer
{SYNAPSE_ADMIN_TOKEN}`. Сам access-токен Matrix сервис не получает и не
хранит — только устанавливает пароль и возвращает его клиенту, а дальше
клиент сам логинится в Synapse обычным `m.login.password`. Это разумный
минимум привилегий: сервис входа не видит токенов сессий Matrix, только
админ-токен (который не выходит за пределы сервера, он не возвращается
клиенту). Инфраструктурно это подкреплено `docker-compose.yml:9` (Synapse
слушает `127.0.0.1:8008`, то есть не публикуется наружу) и
`nginx/default.conf:6-8` (явный `return 403` на `/_synapse/admin`). Замечаний
по самому этому участку нет.

2. **P2.** Вариант А (рекомендую): поменять значение по умолчанию в
   `.env.example` на `DEV_MODE=false`, чтобы случайно не опубликовать
   тестовый режим. Вариант Б: оставить `true` по умолчанию, но добавить явную
   проверку «если `SERVER_NAME` похож на публичный домен — предупреждать».
   Вариант А проще и безопаснее, предлагаю его, но решение за владельцем,

3. **P4.** Нужно решить, добавлять ли лимит по IP/глобальный лимит. Варианты:
   простой счётчик по IP в памяти (минимальное изменение, слабее при
   нескольких исходящих IP у одного клиента) или `slowapi`/внешний rate
   limiter (точнее, но новая зависимость — сознательно не добавляю её сам,
   т.к. задача просила не вводить новый сервис без согласования). Рекомендую
   простой счётчик по IP как минимальную меру для пилота.
4. **P6.** Нужно либо не удалять сессию до успешного `ensure_matrix_user`

   идемпотентность), либо хранить статус «ошибка выдачи, повторите» вместо
   `410`. Рекомендую второй вариант как более явный для пользователя.
5. **P5.** Минимально — задокументировать поведение в README/комментарии;
   менять логику не обязательно для пилота внутри Казахстана.

CREATE TABLE IF NOT EXISTS sessions (
    sid TEXT PRIMARY KEY,

**Состояния экрана** (конечный автомат, без изменения уже заданного
протокола):
`idle` → (ввод номера, нажатие «Продолжить») → `waiting_whatsapp` (есть
`code`, `wa_link`, запущен поллинг `/auth/status` раз в 2 секунды) →
  - код подтверждён → `logging_in` → успешный `client.login` → `done`;
  - `login` в Synapse упал (сеть/неверный ответ) → `error_retryable`, кнопка
    «Повторить» без нового запроса кода;
  - `GET /auth/status` вернул `410` → `expired`, кнопка «Начать заново»
    (сброс к `idle`);
  - нет сети при поллинге (исключение `http.get`) → `error_network`, кнопка
    «Повторить проверку» (не сбрасывать код, просто повторить `status`);
  - пользователь нажал «Отмена» → остановить таймер, вернуться в `idle`,
    сервер явно не уведомляется (эндпоинта отмены нет — это можно обсудить
    отдельно, не блокирует пилот).

Черновик в `flutter/phone_login_page.dart` уже закрывает большинство этих
состояний (`_start`, `_poll`, обработку `410` и сетевых ошибок — строки
42-97 в этом файле), но: (а) не был сверен с реальными `lib/pages/sign_in/` и
`lib/widgets/matrix.dart`, (б) не имеет состояния «Отмена» и не покрыт
тестами. Минимальный объём изменений FluffyChat: один новый файл-страница +
одна новая кнопка в существующем экране входа, без изменения остальной
логики аутентификации.
