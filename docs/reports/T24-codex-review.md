## Проблемы

- **Каталог SSH-ключа** — строки 122–146 исходного отчёта используют
  `%USERPROFILE%\.ssh`. T24 требует хранить ключ под
  `C:\Users\user\Documents\Tildes` за пределами Git. Это несоответствие
  карточке, а не свидетельство утечки. Исправить все связанные команды;
  приватный и публичный ключи различаются по назначению, как описано в
  [Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement).
- **Проверка SSH недостаточна** — строка 146 допускает пароль и другие
  настроенные ключи. Вывод `echo` не доказывает вход указанным ключом.
  Для контрольного подключения нужны изоляция конфигурации, только
  публичный ключ, отсутствие интерактивных запросов и проверка кода выхода.
  Значение этих параметров подтверждает
  [руководство OpenSSH](https://man.openbsd.org/ssh_config.5).
  Для зашифрованного ключа отдельно описать предварительную разблокировку:
  отсутствие пароля Ubuntu не означает отсутствие кодовой фразы ключа.
- **Подлинность сервера** — строка 135 предлагает сразу ответить `yes`.
  Перед этим владелец должен сверить отпечаток с доверенной консолью ВМ;
  порядок проверки указан в
  [OpenSSH: verifying host keys](https://man.openbsd.org/ssh.1#VERIFYING_HOST_KEYS).
  Если используется проектный `known_hosts`, его путь должен совпадать
  при первоначальном принятии ключа и последующем строгом подключении.
- **Права Docker** — строка 187 включает добавление в группу `docker`
  в обязательную последовательность. Эта группа даёт права уровня root,
  что прямо указано в
  [Docker: Linux post-installation steps](https://docs.docker.com/engine/install/linux-postinstall/).
  По правилам проекта решение сначала согласует владелец. Для текущего
  теста достаточно `sudo docker run hello-world`; расширение прав не нужно.
- **Несогласованный переход на NAT** — строка 225 советует менять режим
  сразу при Wi-Fi, хотя T24 разрешает это после подтверждённой проблемы
  bridge. Контрольный SSH и чек-лист также предполагают только NAT,
  несмотря на отдельную инструкцию для работающего bridge.
- **Гарантия о дисках неверна** — строки 43 и 49 безусловно исключают
  доступ к физическим дискам. VirtualBox поддерживает raw disk access,
  описанный в [Oracle: Advanced Topics](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/AdvancedTopics.html).
  Нужна проверка подключённого виртуального накопителя до форматирования,
  без повторной разметки уже установленной ВМ. Наличие raw-диска именно
  в этой ВМ не установлено и не предполагается.

Отсутствие выполненных проверок ВМ не является нарушением T24:
они запрещены карточкой и честно отмечены исполнителем «не проверено».
Памятка требует исправлений до выдачи её команд владельцу.
